## 3. Paradoks

Hibernate Hikari connection ile aynı `SPRING_DATASOURCE_PASSWORD` (len=43) ile **bağlanabiliyor** (auth-service Started 58.3s clean, /api/v1/authz/me 401 anonymous expected). Ama Flyway `FlywayMigrationInitializer` ile aynı password **fail** ediyor.

İki driver/connection mechanism aynı password için farklı sonuç veriyor. Bu D1.1c RCA'nın merkezi.

> ⚠️ **Phase 3 düzeltmesi (2026-05-16)**: "Paradoks" yanlış teşhismiş — gerçek bir paradoks değil. Lazy path **çalışmıyor**; sadece startup'ta DB bağlantısı *zorlamadığı* için credential drift'i maskeliyor. Kök neden credential drift; eager init (Flyway/`validate`) drift'i yalnızca *görünür kılıyor*. Bkz. §5.Y.

## 4. Hipotezler (test edilmesi gereken sırayla)

> ⚠️ **Phase 3 sonucu (2026-05-16)**: H1 (base64 padding) **NEGATIVE** (pod-env = Secret, sha256 match); H6 (Spring property cache stale) **geri çekildi** (değer doğru taşınıyor — değerin *kendisi* yanlış); H2 (eager/lazy) yalnızca *görünürlük* mekanizması, kök neden değil. Gerçek kök neden: **credential drift** — §5.Y.

### H1: Base64 padding kaybı

- Vault canonical password: 44-char base64 (`<...>=` padding ile)
- Pod env `SPRING_DATASOURCE_PASSWORD`: 43 char (`=` kayıp)
- PG SCRAM-SHA-256 auth: password bytes önemli; 43 vs 44 byte SCRAM hash farklı → fail
- **Test plan**: 
  1. Vault'tan password'ü read et (raw bytes), 44 byte mi?
  2. Pod env decode pattern: ESO → K8s Secret → envFrom → pod env. Hangi noktada `=` kayıp?
  3. PG'deki platform user'ın current SCRAM hash'i: `SELECT rolname, rolpassword FROM pg_authid WHERE rolname='platform'` (superuser gerek)
  4. Hash hangi byte stream ile generate edilmişti?

### H2: Hibernate retry mekanizması maskelemesi

- HikariCP connection pool init: ilk fail → retry → eventually success
- Flyway connection: tek shot, retry yok → ilk fail kalıcı
- **Test plan**: 
  1. Auth-service Hibernate boot log'da connection retry mesajı var mı?
  2. HikariCP `connection-init-sql` veya retry config kontrol

### H3: Flyway driver farklı authentication

- Flyway kendi `JdbcConnectionFactory` kullanır, datasource bean'i değil
- Spring Boot autoconfig: `spring.flyway.url`/`user`/`password` set ise → onları; değilse → `spring.datasource.*`
- **Test plan**: 
  1. Spring Boot Flyway autoconfig kaynak code: hangi DataSource bean inject?
  2. `application-k8s.yml` veya `application.properties` Flyway sub-config trace

### H4: ESO Secret refresh timing race

- Pod restart sırasında ESO secret cache stale snapshot kullanmış olabilir
- HikariCP lazy init (connection ihtiyacı olduğunda açar)
- Flyway eager init (Spring Boot startup'ta hemen migrate)
- **Test plan**: 
  1. ESO Secret `lastSync` timestamp vs pod creation time
  2. ESO refresh sırasında Secret data değişimi yakalanabilir mi?

### H5: Network policy / DNS

- Flyway DB hostname farklı resolve ediyor olabilir
- Spring Boot `spring.flyway.url` default → `spring.datasource.url` (aynı host)
- **Düşük olasılık** (URL aynı olmalı)

## 5.X Phase 2 Live Evidence (2026-05-14 Session 49 continuation)

`LOGGING_LEVEL_ORG_FLYWAYDB=DEBUG + LOGGING_LEVEL_COM_ZAXXER_HIKARI=DEBUG` ile pod boot retry:

```
PostgreSQL JDBC Driver 42.7.7

setPrepareThreshold = 5
↓
PSQLException: FATAL: password authentication failed for user "platform"
  at PgConnection.<init>
  at DriverDataSource.getConnection
  at HikariPool.createPoolEntry
  at HikariPool.checkFailFast
  at HikariPool.<init>
  at HikariDataSource.getConnection
  at JdbcUtils.openConnection
  at JdbcConnectionFactory.<init>
  at FlywayExecutor.execute
  at Flyway.migrate
  at FlywayMigrationInitializer.afterPropertiesSet
```

**Kritik bulgu**: 
- Flyway **HikariPool-1** (primary DataSource) kullanıyor — separate DataSource bean değil (H3 NEGATIVE confirmed)
- `HikariPool.checkFailFast` — Hikari **fail-fast** mode aktif: ilk connection denemede başarısız → tüm pool init fail
- Hibernate (DDL_AUTO=none mode'da) **lazy connection**: HikariCP pool config hazırlanır ama gerçek connection açılmaz; pod Running olur; ilk gerçek query'de connection açar → SUCCESS

**H2 CONFIRMED** (Hibernate lazy vs Flyway eager init timing):
- DDL_AUTO=none + FLYWAY=false: Hibernate eager validation yok → Hikari lazy connection → pod Started clean (58.3s)
- DDL_AUTO=validate + FLYWAY=true: Flyway `migrate()` eager → Hikari eager init → checkFailFast → boot fail
- Aynı password, aynı pool, sadece **eager init timing farkı**

**Açık soru**: Hikari neden password authentication failed döner?
- Pod env `SPRING_DATASOURCE_PASSWORD` doğru (44 byte, host'tan psql ile test edildi — manual PASS)
- HikariCP password resolution Spring Boot environment property chain'i kullanıyor olmalı
- **Spring Boot Flyway autoconfig eager init sırasında property resolution stale value alıyor olabilir** (H4 timing race candidate)

**Yeni hipotez H6**: HikariCP DriverDataSource.getConnection() password string'i **runtime resolve** ediyor ama Spring `@Value` veya `Environment.getProperty()` cache'i Flyway init sırasında **eski env value** alıyor olabilir. Pod env güncel ama Spring property cache stale.

## 5.Y Phase 3 — RCA RESOLUTION (2026-05-16): Credential Drift

> **Codex review**: thread `019e32d8-e3db-7b41-9c9b-a2b536b8b95b` — VERDICT **REVISE absorbed** (RCA + fix değeri AGREE; Vault write operator-only; Flyway re-enable + consolidation follow-up).

### 5.Y.1 Test metodu

`DDL_AUTO=validate` ile **izole debug pod** — canlı `auth-service` Deployment'a sıfır temas: bare `Pod`, aynı `envFrom` (ConfigMap `auth-service-config` + Secret `auth-service-secrets`), inline override `SPRING_JPA_HIBERNATE_DDL_AUTO=validate`. `validate` read-only eager Hibernate connection'ı zorlar; Flyway `migrate()` schema mutasyonu olmadan eager-connection davranışı test edilir.

Canlı Deployment strategy `maxSurge:0` → Deployment üzerinde Flyway-enable testi **outage riski** taşır (eski pod önce ölür). Bu yüzden izole debug pod tercih edildi.

İlk debug pod denemesi `UnknownHostException: postgres` ile düştü: bare pod `app.kubernetes.io/part-of=platform` label'ı taşımıyordu → `default-deny-egress` NetworkPolicy DNS egress'i blokladı. Label eklenip yeniden koşuldu (test harness eksikliği, D1.1b bug'ı değil).

### 5.Y.3 Kök neden

**Credential drift.** PG `platform` rolünün gerçek password'ü `808bc9ef…` hash'li değer (4 kardeş servis canlı kullanıyor + direct SCRAM testi `auth_db` için doğruladı). auth-service'in Vault path'i `kv/platform/auth-service` property `db_password` **yanlış değer** (`fddb842b…`) taşıyor.

- D1.1b "Flyway boot fail" = eager DB connection drift'i **görünür kıldı** (sebep değil).
- `DDL_AUTO=none + FLYWAY=false` config'i drift'i **maskeler** — startup'ta connection zorlanmadığı için pod "temiz" boot eder; auth-service'in DB layer'ı işlevsiz ama görünmez (`auth_audit_events` 0 satır kanıtı).
- §3 "paradoksu" yanlış teşhis: lazy path *çalışmıyor*, sadece *denemiyor*.
- **H1** (base64 truncation) NEGATIVE — pod-env ve Secret byte-byte özdeş (sha256 match, 44 byte).
- **H6** (Spring property cache stale) geri çekildi — değer doğru taşınıyor; değerin *kendisi* yanlış.
- **H2** (eager/lazy) yalnızca görünürlük mekanizması — kök neden değil.
- RB-d1.1a runbook'unun `6f765b6d…` hedefi de aynı maskeleme tuzağının ürünü misdiagnosis (o inline değer hiç `scram-sha-256`'ya karşı test edilmemişti) — runbook **retracted**.

### 5.Y.4 Fix planı (Codex AGREE)

`platform` tek paylaşımlı PG rol → tek password. auth-service o değere converge etmeli:

1. **[OPERATOR]** Vault `kv/platform/auth-service` `db_password` → canonical `platform` password (`= kv/platform/user-service/db_password`). Mekanizma: `scripts/ops/platform-ops-vault-patch.sh` (`platform-bootstrap-writer` AppRole, root token YOK). Runbook: `docs/runbooks/RB-d1.1c-auth-service-credential-convergence.md`.
2. **[AGENT]** ESO force-sync `auth-service-secrets` → hash parity verify (prefix `808bc9ef`).
3. **[AGENT]** auth-service rollout restart.
4. **[AGENT]** Post-fix proof: izole debug pod `DDL_AUTO=validate` veya direct TCP/SCRAM → bağlantı başarılı + auth-service log'da auth-fail yok.
5. PG `platform` rolüne **DOKUNULMAZ** (4 servis bağımlı; `ALTER ROLE` yanlış blast radius).

### 5.Y.5 Scope ayrımı (Codex Q5)

- **D1.1c Phase 3 = sadece credential convergence.** Acceptance: ESO hash parity + rollout + DB connection proof.
- **Flyway re-enable + baseline = ayrı follow-up.** `auth_db` non-empty + `flyway_schema_history` yok → `baseline-on-migrate` kararı, schema dump, platform-backend migration inventory, schema diff ayrı plan gerektirir. Tek değişiklikte secret convergence + Flyway schema authority birlikte değiştirilmez.

Önerilen: shared canonical Vault path (yalnız `db_username`/`db_password`); service-specific alanlar (JWT, KC client secret, internal API key) kendi path'lerinde kalır. Uzun vade: per-service dedicated PG roles (büyük blast radius, ayrı faz).
