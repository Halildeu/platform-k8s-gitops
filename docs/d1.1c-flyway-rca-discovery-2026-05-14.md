## 2. Preflight kanıtları

### 2.1 PG host auth (manual)

```bash
$ docker exec platform-pg-test psql -U platform -d auth_db -c 'SELECT current_user'
# Pwd source: kubectl get secret auth-service-secrets ... | base64 -d
# Pwd len: 44
# Auth: PASS
# Result: platform | auth_db
```

PG'deki `platform` user + Secret value ile auth **çalışıyor** (host'tan).

### 2.2 In-pod env inspection

```
SPRING_DATASOURCE_PASSWORD len=43
SPRING_DATASOURCE_USERNAME len=8       (= "platform")
SPRING_DATASOURCE_URL      len=39
SPRING_FLYWAY_ENABLED      len=5       (= "false" — recovery state)
SPRING_FLYWAY_USER         — YOK

SPRING_FLYWAY_URL          — YOK
```

**Anomali**: pod env `SPRING_DATASOURCE_PASSWORD len=43` vs host decode `len=44`.

Olası neden: `=` base64 padding kaybı (Kubernetes Secret base64 render ↔ pod env injection chain).

### 2.3 Flyway-specific env not set

`SPRING_FLYWAY_USER/PASSWORD/URL` env'leri yok → Spring Boot Flyway autoconfig default `spring.datasource.*` inherit etmesi gerek. application.properties'te de set değil.

## 3. Paradoks

Hibernate Hikari connection ile aynı `SPRING_DATASOURCE_PASSWORD` (len=43) ile **bağlanabiliyor** (auth-service Started 58.3s clean, /api/v1/authz/me 401 anonymous expected). Ama Flyway `FlywayMigrationInitializer` ile aynı password **fail** ediyor.

İki driver/connection mechanism aynı password için farklı sonuç veriyor. Bu D1.1c RCA'nın merkezi.

## 4. Hipotezler (test edilmesi gereken sırayla)

### H1: Base64 padding kaybı

- Vault canonical password: 44-char base64 (`<...>=` padding ile)
- Pod env `SPRING_DATASOURCE_PASSWORD`: 43 char (`=` kayıp)
- PG SCRAM-SHA-256 auth: password bytes önemli; 43 vs 44 byte SCRAM hash farklı → fail
- **Test plan**: 
  1. Vault'tan password'ü read et (raw bytes), 44 byte mi?
  2. Pod env decode pattern: ESO → K8s Secret → envFrom → pod env. Hangi noktada `=` kayıp?
  3. PG'deki platform user'ın current SCRAM hash'i: `SELECT rolname, rolpassword FROM pg_authid WHERE rolname='platform'` (superuser gerek)
  4. Hash hangi byte stream ile generate edilmişti?

### H2: Hibernate retry mekanizması maskelemesi

- HikariCP connection pool init: ilk fail → retry → eventually success
- Flyway connection: tek shot, retry yok → ilk fail kalıcı
- **Test plan**: 
  1. Auth-service Hibernate boot log'da connection retry mesajı var mı?
  2. HikariCP `connection-init-sql` veya retry config kontrol

### H3: Flyway driver farklı authentication

- Flyway kendi `JdbcConnectionFactory` kullanır, datasource bean'i değil
- Spring Boot autoconfig: `spring.flyway.url`/`user`/`password` set ise → onları; değilse → `spring.datasource.*`
- **Test plan**: 
  1. Spring Boot Flyway autoconfig kaynak code: hangi DataSource bean inject?
  2. `application-k8s.yml` veya `application.properties` Flyway sub-config trace

### H4: ESO Secret refresh timing race

- Pod restart sırasında ESO secret cache stale snapshot kullanmış olabilir
- HikariCP lazy init (connection ihtiyacı olduğunda açar)
- Flyway eager init (Spring Boot startup'ta hemen migrate)
- **Test plan**: 
  1. ESO Secret `lastSync` timestamp vs pod creation time
  2. ESO refresh sırasında Secret data değişimi yakalanabilir mi?

### H5: Network policy / DNS

- Flyway DB hostname farklı resolve ediyor olabilir
- Spring Boot `spring.flyway.url` default → `spring.datasource.url` (aynı host)
- **Düşük olasılık** (URL aynı olmalı)

## 5.X Phase 2 Live Evidence (2026-05-14 Session 49 continuation)

`LOGGING_LEVEL_ORG_FLYWAYDB=DEBUG + LOGGING_LEVEL_COM_ZAXXER_HIKARI=DEBUG` ile pod boot retry:

```
HikariPool-1 - Attempting to create/setup new connection (2ede42f1-73be-4aa0-ab22-b459559a2c1a)
PostgreSQL JDBC Driver 42.7.7
setDefaultFetchSize = 0
setPrepareThreshold = 5
↓
PSQLException: FATAL: password authentication failed for user "platform"
  at PgConnection.<init>
  at DriverDataSource.getConnection
  at HikariPool.createPoolEntry
  at HikariPool.checkFailFast
  at HikariPool.<init>
  at HikariDataSource.getConnection
  at JdbcUtils.openConnection
  at JdbcConnectionFactory.<init>
  at FlywayExecutor.execute
  at Flyway.migrate
  at FlywayMigrationInitializer.afterPropertiesSet
```

**Kritik bulgu**: 
- Flyway **HikariPool-1** (primary DataSource) kullanıyor — separate DataSource bean değil (H3 NEGATIVE confirmed)
- `HikariPool.checkFailFast` — Hikari **fail-fast** mode aktif: ilk connection denemede başarısız → tüm pool init fail
- Hibernate (DDL_AUTO=none mode'da) **lazy connection**: HikariCP pool config hazırlanır ama gerçek connection açılmaz; pod Running olur; ilk gerçek query'de connection açar → SUCCESS

**H2 CONFIRMED** (Hibernate lazy vs Flyway eager init timing):
- DDL_AUTO=none + FLYWAY=false: Hibernate eager validation yok → Hikari lazy connection → pod Started clean (58.3s)
- DDL_AUTO=validate + FLYWAY=true: Flyway `migrate()` eager → Hikari eager init → checkFailFast → boot fail
- Aynı password, aynı pool, sadece **eager init timing farkı**

**Açık soru**: Hikari neden password authentication failed döner?
- Pod env `SPRING_DATASOURCE_PASSWORD` doğru (44 byte, host'tan psql ile test edildi — manual PASS)
- HikariCP password resolution Spring Boot environment property chain'i kullanıyor olmalı
- **Spring Boot Flyway autoconfig eager init sırasında property resolution stale value alıyor olabilir** (H4 timing race candidate)

**Yeni hipotez H6**: HikariCP DriverDataSource.getConnection() password string'i **runtime resolve** ediyor ama Spring `@Value` veya `Environment.getProperty()` cache'i Flyway init sırasında **eski env value** alıyor olabilir. Pod env güncel ama Spring property cache stale.

Phase 3 test plan:
1. `SPRING_DATASOURCE_PASSWORD` env'i explicit non-Vault literal'a set + Flyway retry
2. Eğer çalışıyorsa H6 confirmed (property timing); eğer fail olursa daha derin debugging
3. Backend `HikariConfig.getPassword()` çağrı stack'ini trace
