# Notification Event Contract — Faz 23.0

> **Status**: DRAFT (Faz 23.0 charter — 2026-05-05)
> **ADR**: [ADR-0013-notification-orchestration](../adr/0013-notification-orchestration.md)
> **Codex thread**: `019df86f-89aa-7200-bb6c-b7b903860148`

Bu doküman platform içi servislerin **notification-orchestrator** ile konuşma **kontratı**dır. Domain servisleri provider'ı **direkt çağırmaz** — bu contract üzerinden notification intent yayar.

---

## 1. Üst Düzey Akış

```
[Domain Service]                       [notification-orchestrator]
      │                                          │
      │  1. Domain transaction                   │
      │     (örn. password reset request)        │
      │                                          │
      ├─▶ outbox row INSERT                      │
      │   (transactional with domain DB)         │
      │                                          │
      │                                          │
      │   2. Outbox poll cycle                   │
      │   (PG advisory lock, ≤2s)                │
      │◀─────────────────────────────────────────┤
      │                                          │
      ├─▶ notification_intent INSERT             │
      │   (idempotency_key + payload)            │
      │                                          │
      │   3. Process intent                      │
      │   - Template resolve                     │
      │   - Subscriber preference check          │
      │   - OpenFGA can_receive check            │
      │   - Provider select                      │
      │   - Channel adapter call                 │
      │                                          │
      │   4. delivery row INSERT                 │
      │   - status (PENDING/DELIVERED/FAILED)    │
      │   - provider_msg_id                      │
      │   - retry_count                          │
      │                                          │
      │   5. audit_event row INSERT              │
      │   - PII redacted                         │
      │   - correlation_id                       │
```

## 3. Field Specifications

### `intent_id` (zorunlu)

- Format: ULID veya UUID v4
- Generated by domain service or auto-assigned at orchestrator
- Globally unique
- Used for `correlation_id` chaining if not separately set

### `idempotency_key` (zorunlu)

- Format: string, max 255 char
- Convention: `<topic_key>-<recipient_id>-<source_event_unique_part>`
- Window: 24h default (D30-NOTIFY duplicate replay guard)
- Aynı key ile ikinci intent → no duplicate delivery, audit row `BLOCKED_BY_IDEMPOTENCY`

### `correlation_id` (opsiyonel ama önerilir)

- Format: trace-id (W3C Trace Context veya custom)
- Distributed tracing için
- Boşsa `intent_id` correlation_id olarak kullanılır

### `org_id` (zorunlu)

- Format: string, max 64 char
- Multi-tenant boundary (D41)
- `default` = platform-wide tenant
- Cross-org notification isteği reddedilir (OpenFGA tuple kontrolü)

### `topic_key` (zorunlu)

- Format: dot-notation, lowercase, kebab-case
- Örnek: `auth.password-reset`, `drift.alarm`, `endpoint-admin.heartbeat-fail`
- **Flat hierarchy** (Codex revize — topic hierarchy v1)
- Subscriber preference + OpenFGA tuple lookup için kullanılır

### `severity` (zorunlu)

| Değer | Anlamı | Örnek |
|---|---|---|
| `info` | Bilgilendirme | onboarding invite, system update notice |
| `warning` | Dikkat gerekiyor | retry limit yaklaşıldı, quota %80 |
| `critical` | Acil aksiyon | drift alarm, break-glass token issued, heartbeat fail |

`critical` severity **quiet hours bypass eder** (D8 preference + D45 critical bypass policy).

### `data_classification` (zorunlu — D45 yeni)

| Değer | Anlamı | Quiet bypass | Marketing kapsamı | Retention default |
|---|---|---|---|---|
| `transactional` | Operasyonel zorunlu (password reset, invoice) | hayır | dışı | 90 gün |
| `security` | Güvenlik kritik (login alert, break-glass) | **evet** | dışı | 180 gün |
| `commercial` | Pazarlama/ticari | hayır | **içinde** (KVKK açık rıza) | 30 gün |
| `system` | Platform sistem mesajı (downtime, maintenance) | hayır | dışı | 30 gün |

### `recipients[]` (zorunlu, en az 1)

İki tip:

**A. Subscriber tipi** (platform user):
```json
{
  "type": "subscriber",
  "subscriber_id": "1204"
}
```

**B. External tipi** (platform-dışı kullanıcı):
```json
{
  "type": "external",
  "email": "newuser@example.com",
  "phone": "+905551234567",
  "name": "Yeni Kullanıcı",
  "locale": "tr-TR"
}
```

External tip için OpenFGA scope check **bypass** edilir (subscriber yok), preference yok, default kanal (email).

### `template` (zorunlu)

```json
{
  "template_id": "auth-password-reset",
  "version": null,
  "locale": "tr-TR"
}
```

- `version: null` → en güncel aktif versiyon
- `version: 5` → spesifik versiyonu kilitle (rollback senaryosu)
- `locale` → fallback chain: `tr-TR` → `tr` → `en-US` → `en` → default

### `channels[]` (zorunlu, en az 1)

Geçerli değerler (D44 tier'a göre):

| Tier | Kanallar |
|---|---|
| Kernel/Closed Beta | `email`, `slack`, `webhook` |
| Production MVP geniş | + `sms`, `in-app` |
| v1 | + `teams`, `web-push`, `push-fcm`, `push-apns` |
| v2 | + `whatsapp`, `voice`, `pwa` |

### `channel_routing` (opsiyonel)

```json
{
  "strategy": "fan_out",
  "priority": ["email", "sms"],
  "fallback_on_fail": true
}
```

| `strategy` | Anlamı |
|---|---|
| `single` | Sadece `channels[0]` denenir |
| `fan_out` | Tüm kanallara aynı anda gönder (varsayılan) |
| `priority_fallback` | İlk kanalı dene, fail ise `priority[1]`, vb. (v1) |

### `payload` (zorunlu)

Template variable interpolation için. Sade key-value:

```json
{
  "user_name": "Halil",
  "reset_url": "https://...",
  "expires_at": "2026-05-05T15:00:00Z",
  "amount": 1234.56,
  "items": ["Ürün A", "Ürün B"]
}
```

**KVKK kuralı**: Payload PII içerebilir (template substitution için). `audit_event` tablosuna **redacted** olarak yazılır:
- `user_name` → `<REDACTED>`
- `reset_url` → `<URL_HASH>`
- Salt değerler korunur, kişisel bilgi maskelenmiş

### `scheduled_at` / `expire_at` (opsiyonel — v1)

- `scheduled_at`: ISO 8601, ileri tarih → poller bu zamana kadar PENDING tutar
- `expire_at`: ISO 8601, bu zamandan sonra ENVELOPE_EXPIRED status (gönderilmez)

### `metadata` (opsiyonel)

Source domain bilgisi audit/debug için. PII içermez.

### `preference_override` (opsiyonel — kısıtlı)

```json
{
  "bypass_quiet_hours": true,
  "bypass_frequency_limit": false
}
```

- `bypass_quiet_hours`: yalnız `severity: critical` veya `data_classification: security` için izinli
- `bypass_frequency_limit`: yalnız `severity: critical` için izinli
- Validation: orchestrator override geçerliliğini check eder; geçersizse 400 + audit `INVALID_OVERRIDE`

## 4. PostgreSQL Schema (Faz 23.1 V1__init_notify_schema.sql özet)

### `notify.notification_intent`

```sql
CREATE TABLE notify.notification_intent (
  id BIGSERIAL PRIMARY KEY,
  intent_id VARCHAR(64) NOT NULL UNIQUE,
  idempotency_key VARCHAR(255) NOT NULL,
  correlation_id VARCHAR(128),
  org_id VARCHAR(64) NOT NULL,
  topic_key VARCHAR(128) NOT NULL,
  severity VARCHAR(16) NOT NULL,
  data_classification VARCHAR(16) NOT NULL,
  payload JSONB NOT NULL,
  template_id VARCHAR(128) NOT NULL,
  template_version INT,
  locale VARCHAR(16) NOT NULL,
  channels TEXT[] NOT NULL,
  channel_routing JSONB,
  scheduled_at TIMESTAMPTZ,
  expire_at TIMESTAMPTZ,
  metadata JSONB,
  preference_override JSONB,
  status VARCHAR(20) NOT NULL DEFAULT 'PENDING',  -- PENDING/PROCESSING/COMPLETED/EXPIRED
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW(),
  CONSTRAINT uq_intent_idempotency UNIQUE (org_id, idempotency_key)
);

CREATE INDEX idx_intent_status_scheduled ON notify.notification_intent (status, scheduled_at);
CREATE INDEX idx_intent_org_topic ON notify.notification_intent (org_id, topic_key);
CREATE INDEX idx_intent_correlation ON notify.notification_intent (correlation_id);
```

### `notify.notification_delivery`

```sql
CREATE TABLE notify.notification_delivery (
  id BIGSERIAL PRIMARY KEY,
  intent_id VARCHAR(64) NOT NULL REFERENCES notify.notification_intent(intent_id),
  channel VARCHAR(32) NOT NULL,
  recipient_type VARCHAR(16) NOT NULL,  -- subscriber/external
  recipient_id VARCHAR(128),
  recipient_hash VARCHAR(64) NOT NULL,  -- sha256 of address (PII redaction)
  provider VARCHAR(64) NOT NULL,
  provider_msg_id VARCHAR(255),
  status VARCHAR(20) NOT NULL,  -- PENDING/DELIVERED/FAILED/BOUNCED/BLOCKED_BY_PREFERENCE/BLOCKED_BY_AUTHZ/BLOCKED_BY_IDEMPOTENCY
  attempt_count INT DEFAULT 0,
  last_attempt_at TIMESTAMPTZ,
  delivered_at TIMESTAMPTZ,
  failure_reason TEXT,
  next_retry_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_delivery_intent ON notify.notification_delivery (intent_id);
CREATE INDEX idx_delivery_status_retry ON notify.notification_delivery (status, next_retry_at);
CREATE INDEX idx_delivery_recipient_hash ON notify.notification_delivery (recipient_hash);
```

### `notify.audit_event`

```sql
CREATE TABLE notify.audit_event (
  id BIGSERIAL PRIMARY KEY,
  intent_id VARCHAR(64) NOT NULL,
  delivery_id BIGINT,
  event_type VARCHAR(64) NOT NULL,  -- INTENT_CREATED, DELIVERY_ATTEMPTED, DELIVERY_SUCCEEDED, DELIVERY_FAILED, BLOCKED_BY_*, OVERRIDE_REJECTED, etc.
  org_id VARCHAR(64) NOT NULL,
  topic_key VARCHAR(128) NOT NULL,
  recipient_hash VARCHAR(64),
  channel VARCHAR(32),
  template_id VARCHAR(128),
  template_version INT,
  details JSONB,  -- redacted; no PII
  correlation_id VARCHAR(128),
  occurred_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_audit_org_topic ON notify.audit_event (org_id, topic_key, occurred_at);
CREATE INDEX idx_audit_recipient ON notify.audit_event (recipient_hash, occurred_at);
CREATE INDEX idx_audit_correlation ON notify.audit_event (correlation_id);
CREATE INDEX idx_audit_occurred ON notify.audit_event (occurred_at);  -- retention/erasure scan

-- Append-only enforcement (D46 must-have #10)
CREATE RULE audit_event_no_update AS ON UPDATE TO notify.audit_event DO INSTEAD NOTHING;
CREATE RULE audit_event_no_delete AS ON DELETE TO notify.audit_event DO INSTEAD NOTHING;
```

### Domain-side `outbox` (örnek pattern)

Her domain service kendi outbox'ını yönetir:

```sql
CREATE TABLE auth.notification_outbox (
  id BIGSERIAL PRIMARY KEY,
  intent_payload JSONB NOT NULL,  -- ready-to-send NotificationIntent
  status VARCHAR(20) NOT NULL DEFAULT 'PENDING',  -- PENDING/PROCESSED/FAILED
  retry_count INT DEFAULT 0,
  next_retry_at TIMESTAMPTZ,
  failure_reason TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  processed_at TIMESTAMPTZ
);

CREATE INDEX idx_auth_outbox_pending ON auth.notification_outbox (status, next_retry_at);
```

Domain service transactional INSERT (kendi DB transaction'ında):
```java
@Transactional
public void requestPasswordReset(...) {
  authRepository.saveResetToken(...);
  outboxRepository.save(NotificationOutboxRow.builder()
    .intentPayload(buildIntent(user, token))
    .build());
}
```

`notification-orchestrator` outbox poller her domain'in outbox'ını ayrı poll eder (PG advisory lock); intent_payload'u `notification_intent`'e taşır.

## 5. REST API

### `POST /api/v1/notify/intents` — Intent submit

**Body**: yukarıdaki JSON schema.

**Response 202 Accepted**:
```json
{
  "intent_id": "01HXYZAB...",
  "status": "ACCEPTED",
  "tracking_url": "/api/v1/notify/intents/01HXYZAB..."
}
```

**Response 400** — invalid (missing required field, invalid override, expired)
**Response 409** — duplicate idempotency_key (returns previous intent_id)
**Response 403** — OpenFGA cross-tenant deny
**Response 429** — rate limit per source

## 6. Idempotency + Dedupe (D46 #2)

| Senaryo | Davranış |
|---|---|
| Aynı `idempotency_key` 24h içinde 2. kez | Original intent_id döndür; no duplicate delivery; audit `BLOCKED_BY_IDEMPOTENCY` |
| Aynı `idempotency_key` 24h sonra | Yeni intent kabul; idempotency window sona erdi |
| Domain outbox replay (poller crash sonrası) | Outbox row idempotent; orchestrator dedupe ile kontrol eder |
| Saga retry | `idempotency_key` aynı → no duplicate; tracking response yine 202 ile original intent_id |

Dedupe key (v1): `(template_id + recipient_hash + payload_sha256)` — same template same recipient same content 5dk içinde 2. kez → audit `DEDUPED`.

## 7. PII Redaction Policy (D42 + D46 #7)

### Log girişlerinde

❌ **YASAK**:
```
INFO: Sending email to halil@example.com with body 'Your reset token is ABC123'
```

✅ **DOĞRU**:
```
INFO: intent_id=01HXY... org_id=default topic=auth.password-reset 
      channel=email recipient_hash=a3f8c... template_id=auth-password-reset 
      template_version=3 status=DELIVERED provider=smtp-corporate latency_ms=234
```

### `audit_event.details` JSONB

❌ **YASAK** (PII içeren):
```json
{
  "user_email": "halil@example.com",
  "reset_url": "https://testai.acik.com/reset?token=ABC123"
}
```

✅ **DOĞRU** (redacted):
```json
{
  "recipient_hash": "a3f8c...",
  "url_template": "/reset?token=<TOKEN>",
  "delivery_latency_ms": 234,
  "provider_response_code": 250
}
```

### `notification_intent.payload` JSONB

PII içerebilir (template substitution için zorunlu) ama:
- DB encryption at rest (storage seviyesi — D45 infra prerequisite)
- Sadece orchestrator process content erişir; log ekrana yansıtılmaz
- KVKK Art.11 erasure → payload field NULL'lanır, kalan metadata audit'te kalır

## 8. Outage Fallback Bypass (D43 + D46 #10)

`notification-orchestrator` down olduğunda, bu domain servisleri Alertmanager direct kanalını kullanır:

| Domain | Fallback kanalı |
|---|---|
| Drift alarm-receiver | Alertmanager → Slack `#alerts` direct webhook (kendi Vault credential'ı) |
| Break-glass token issuance | Alertmanager → SMTP corporate relay direct (kendi Vault credential'ı) |
| Critical heartbeat-fail (Faz 22) | Alertmanager → Slack direct |

Alertmanager rule örneği:
```yaml
- alert: NotificationOrchestratorDown
  expr: up{job="notification-orchestrator"} == 0
  for: 5m
  annotations:
    summary: "Notification orchestrator down — switching to direct fallback"
    runbook: "docs/runbooks/RB-notification-outage-fallback.md"
```

Fallback runbook (`RB-notification-outage-fallback.md`) sub-faz 23.2'de yazılır.

## 9. Distributed Tracing (D46 #1)

Her intent + delivery + audit row `correlation_id` taşır. W3C Trace Context standardı:

- HTTP header: `traceparent: 00-<trace-id>-<span-id>-01`
- DB column: `correlation_id VARCHAR(128)`
- Log MDC: `correlation_id` her log entry'de

Query örneği (audit + delivery + intent join):
```sql
SELECT i.intent_id, i.topic_key, i.created_at, d.channel, d.status, a.event_type, a.occurred_at
FROM notify.notification_intent i
JOIN notify.notification_delivery d USING (intent_id)
JOIN notify.audit_event a USING (intent_id)
WHERE a.correlation_id = 'trace-abc-123'
ORDER BY a.occurred_at;
```

## 10. Versioning + Backward Compatibility

- API versiyonu: `/api/v1/notify/...` — major version
- Intent JSON schema: `metadata.contract_version` (default `"1.0"`)
- Template versioning: `template.version` int, immutable
- Provider config versioning: `provider_config.version` int, immutable

Schema değişimi (v2 contract):
- Yeni alanlar opsiyonel olarak eklenir (backward compatible)
- Mevcut alanlar deprecate edilebilir, 6 ay grace period
- Breaking change → `/api/v2/notify/...` ayrı endpoint
